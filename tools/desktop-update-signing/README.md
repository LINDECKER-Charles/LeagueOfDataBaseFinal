# tools/desktop-update-signing

Signing of the release feeds of the desktop app (ADR 0008, guide
`docs/guides/release-desktop.md`). Velopack finds a newer version in `releases.<channel>.json`,
then checks each downloaded package against the size and SHA-256 that feed lists. The app reads
a feed only when its signature holds against one of the public keys compiled into it
(`src/LoDb.Desktop/Updates/Engine/UpdateFeeds.cs`), so the packages are authenticated by the
signed checksums, whoever hosts them.

| Element        | Value                                                                         |
| -------------- | ----------------------------------------------------------------------------- |
| Signature      | Ed25519 (RFC 8032), base64 on one line, in `releases.<channel>.json.sig`      |
| Signed message | `lodb-desktop-feed-v1\n` + the feed's file name + `\n` + the feed's bytes     |
| Private key    | `LODB_DESKTOP_UPDATE_PRIVATE_KEY`: the PKCS#8 PEM, or the PEM in base64       |
| Public keys    | `UpdateFeeds.FeedPublicKeys`: the 32 raw bytes in base64, one key per line    |
| Feed entries   | each one with its `Size` and `SHA256`; without them, the app ignores the feed |

The file name in the message binds a signature to its RID and channel: the feed of
`win-x64-beta` never passes for the one of `win-x64`. The app trusts one key, or two while a
key is rotated (guide § Flux signés). `--public-key` and the `--smoke` report write a set of
keys as one value, the keys separated by spaces.

The release workflow signs in a job that runs neither npm nor the .NET build: these scripts use
the Node built-ins only, and must keep doing so. The tests generate throwaway keys at each run;
none is committed, not even a test one. The fixture under
`tests/LoDb.Desktop.Tests/Updates/Signing/Fixtures` was signed by this tool with a key that was
discarded at once: the app's tests and these ones both verify it.

## Key

Generated by the owner, outside any repository (`generate-key.mjs` refuses a path inside a git
work tree and never overwrites a file):

```sh
node tools/desktop-update-signing/generate-key.mjs --out <secure folder>/feed-signing.pem
gh secret set LODB_DESKTOP_UPDATE_PRIVATE_KEY < <secure folder>/feed-signing.pem
```

It prints the public key only, which goes into `UpdateFeeds.FeedPublicKeys`. Every installed
copy carries those keys: changing one is a rotation (guide § Flux signés). The file is created
with mode 0600, which only Unix honours: on Windows it inherits the ACL of its folder, so
restrict that folder to your own account (`icacls <folder> /inheritance:r /grant:r
"%USERNAME%:(OI)(CI)F"`) and check the file with `icacls <file>`.

## Sign

```sh
LODB_DESKTOP_UPDATE_PRIVATE_KEY="$(cat feed-signing.pem)" \
  node tools/desktop-update-signing/sign-feed.mjs --releases releases --channel win-x64 \
    --version 1.4.0
```

Rewrites `releases/releases.win-x64.json` as the GitHub Release of 1.4.0 publishes it: vpk pack
lists every package of the folder, N-1 fetched for the delta included, while the release holds
only those of its version. Then writes the signature next to it. It refuses a signing key whose
public half is not among the keys compiled into the app; `--public-key` names others for a
local E2E build, which trusts a throwaway key (`-p:LoDbDesktopFeedKey`). It also refuses a
feed holding a key vpk does not write under that exact name: the app matches key names without
case, so such a feed could name one package to these checks and another to the app.

## Verify

```sh
node tools/desktop-update-signing/verify-feed.mjs --releases releases --channel win-x64 \
  [--public-key "BASE64 ..."] [--packages]
```

Checks the signature as the app will, and that every entry carries its size and SHA-256.
`--packages` also checks each listed package of the folder. The release runs it before the
upload, and on the feed it downloads back from the GitHub Release.

`node tools/desktop-update-signing/app-key.mjs` prints the keys compiled into the app, which
the update gate expects to see in the `--smoke` report of the new version.
