### G1 — la CLI de l'hôte plante dans la stack de dev (L7.3) — bloquant pour le lot 7

**Reproduire** :

```bash
docker compose -p lodb-next -f compose.next.yaml -f compose.next.override.yaml \
  exec -T api dotnet LoDb.Api.dll admin create --email e2e@example.com
# idem pour : analytics import --source /x --dry-run ; ingest --version 16.18.1
```

**Sortie utile** :

```text
Unhandled exception. System.AggregateException: Some services are not able to be constructed
(… 'AuthorizationPolicyCache': Unable to resolve service for type
'Microsoft.AspNetCore.Routing.EndpointDataSource' …)
(… 'LoDb.Api.Modules.Admin.Monitoring.ServiceProbes': Unable to resolve service for type
'Microsoft.Extensions.Diagnostics.HealthChecks.HealthCheckService' …)
(… 'LoDb.Api.Modules.Admin.Monitoring.MonitoringReporter': … same …)
   at LoDb.Api.Cli.CliRunner.RunInHostAsync(…) in /source/src/LoDb.Api/Cli/CliRunner.cs:line 83
```

**Analyse** : `compose.next.override.yaml` met l'API en `Development`, où l'hôte générique
de `CliRunner` valide tout le conteneur à sa construction. Les enregistrements de
`AdminModule` (autorisation et sondes de santé, qui n'existent que dans l'hôte web) ne se
résolvent pas hors de Kestrel. Toutes les sous-commandes à hôte tombent, pas seulement
`admin create` : `analytics import` et `ingest` aussi. La même commande avec
`-e ASPNETCORE_ENVIRONMENT=Production` réussit, et c'est ainsi que ce jalon a lancé
`ingest`, `analytics import` et `admin create` (§ 4). Les tests .NET ne le voient pas :
aucun ne construit l'hôte de la CLI en `Development`.

**Effet** : les 29 E2E admin échouent (19) ou ne tournent pas (10), car la fixture crée
chaque administrateur par `admin create`.

**Fichiers suspects** : `src/LoDb.Api/Modules/Admin/AdminModule.cs` (et ses
enregistrements `Monitoring/**`), `src/LoDb.Api/Cli/CliRunner.cs`, un test d'hôte CLI en
`Development` dans `tests/LoDb.Api.Tests/Admin/`.

**Groupe proposé** : G1 = `src/LoDb.Api/Modules/Admin/**`, `src/LoDb.Api/Cli/**`,
`tests/LoDb.Api.Tests/Admin/**`.

   `pg_dump -Fc lodb | pg_restore --no-owner --no-privileges -d lodb_j567`.

   (`docker compose -p lodb-next … run --rm --no-deps -e ConnectionStrings__LoDb=Host=host.docker.internal;…;Database=lodb_j567;… migrate`) :

   pas d'historique d'ingestion.

   `ingest --version 16.18.1 --languages de_DE,es_ES,ko_KR,fr_FR,en_GB,en_US` côté

   (4 comptes, 10 builds, 6 votes).
5. Les deux stacks sur la copie : `.env` local (ignoré par Git) à `POSTGRES_DB=lodb_j567`
   le temps de l'essai ; l'API de `lodb-next` par une surcouche compose temporaire, hors
